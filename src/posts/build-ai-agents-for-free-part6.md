前回、役割分担の本体は「AIの作業机を分けること」だと書きました。今回はその具体的な手順です。

結論から書きます。**Claude Codeの標準機能だけで作れます。追加費用はゼロです。**

プラグインも、有料ツールも、特別な環境構築も要りません。テキストファイルを数枚置くだけです。順番に見ていきます。

## 全体像

作るものは、これだけです。

```
プロジェクトのフォルダ/
├── .claude/
│   └── agents/
│       ├── researcher.md   ← 調査役の指示書
│       ├── writer.md       ← 執筆役の指示書
│       └── reviewer.md     ← 検証役の指示書
└── CLAUDE.md               ← 全体の運用方針
```

**設定ファイル3枚と、方針が1枚。** これで机の分離も、役割分担も、並列実行も動きます。

今回は記事執筆を例にしますが、中身を書き換えれば何にでも使えます。

## STEP1：フォルダを作る

```bash
mkdir -p .claude/agents
```

プロジェクトの直下に置くと、そのプロジェクト専用になります。どこでも使いたい場合は `~/.claude/agents/` に置いてください。

## STEP2：役割ファイルを置く

1枚目、調査役です。

```markdown
.claude/agents/researcher.md
---
name: researcher
description: 事実確認と情報収集の専門家。記事の下調べ段階で使う。
tools: WebSearch, WebFetch, Read, Write
model: sonnet
---
あなたはリサーチャーです。渡されたテーマについて調べてください。

- 一次情報を優先する。まとめサイトや二次情報は根拠にしない
- 数字や固有名詞は、出典URLとセットで記録する
- 確認できなかったことは「不明」と明記する。推測で埋めない
- 結果は事実の箇条書きで返す。解釈や意見は加えない
```

2枚目、執筆役です。

```markdown
.claude/agents/writer.md
---
name: writer
description: 文章作成の専門家。調査が完了した後の執筆段階で使う。
tools: Read, Write, Edit
model: sonnet
---
あなたはライターです。渡された事実に基づいて文章を書いてください。

- 結論を最初に書く
- 一文は40〜60字に収める
- 専門用語には初出時に括弧書きで説明を添える
- 渡された事実にないことは書かない
```

3枚目、検証役です。

```markdown
.claude/agents/reviewer.md
---
name: reviewer
description: 原稿の検証専門家。文章が完成した後に必ず使う。
tools: Read, Grep
model: sonnet
---
あなたは校閲担当です。原稿を検証してください。

- 事実と異なる記述、根拠のない断定を指摘する
- 指摘は「該当箇所」と「なぜ問題か」をセットで示す
- 問題がなければ「PASS」、あれば「FAIL」で明確に判定する
- 文章を勝手に書き換えない。指摘だけを返す
```

### ファイルの読み方

上の `---` で囲まれた部分が設定、その下が指示書の本体です。

| 項目 | 意味 |
|---|---|
| `name` | 呼び出すときの名前 |
| `description` | **どういうときに使うか。ここが自動での振り分けを決める** |
| `tools` | 使わせる道具の範囲（検証役に書き込み権限を与えないのがポイント） |
| `model` | 使うAIモデル |

`description` が最重要です。ここに書いた内容とタスクの内容が一致すると、**指名しなくても自動で振り分けられます。** 逆にここが曖昧だと、いつまでも呼ばれません。

### 書くのが面倒な場合

Claude Codeに直接頼めます。

```
> 原稿の校閲をする専門エージェントを作りたい。
  事実誤認と根拠のない断定を指摘する役割。
```

これだけで、`description`もシステムプロンプトも自動生成してくれます。

## STEP3：CLAUDE.mdに方針を書く

ここが見落とされがちですが、**いちばん効く工程**です。

実は、**明示的な指示がないと、Claude Codeはほとんど役割分担をしません。** 全部自分でやろうとして、1つの机に作業を積み上げてしまいます。せっかくファイルを用意しても、使われずに終わります。

なので、方針を書いて挙動を変えます。

```markdown
# CLAUDE.md

## エージェント運用方針

- 調査が必要な作業は、必ず researcher に委譲する
- 文章の作成は、必ず writer に委譲する
- 文章が完成したら、必ず reviewer に委譲して検証する
- reviewer が FAIL を返した場合は、指摘内容を添えて writer に差し戻す

- 独立して進められる作業が複数ある場合は、
  1つのメッセージ内で複数のタスクを同時に投げ、並列で実行する

- 各エージェントを呼ぶときは、必要な情報をタスクの説明文に必ず含めること。
  エージェントはこれまでの会話を見ることができない
```

最後の1行が重要です。詳しくは後半で説明します。

## STEP4：呼び出す

**まとめて任せる場合：**

```
> 2026年のAI検索の動向について記事を書いて。
  調査から執筆、検証まで通しでお願い。
```

`description` が的確であれば、Claude Codeが自分で「これは調査だから researcher に」「書き終わったから reviewer に」と判断して振り分けます。

**役割を指定する場合：**

```
> researcher を使って、2026年のAI検索の動向を調べて。
```

**並列で走らせる場合：**

```
> 以下を並列で調べて：
  1. 国内の動向
  2. 海外の動向
  3. 主要サービスの機能比較
```

同時に走らせられるのは**最大10件**まで。それを超えた分は、終わったものから順に投入されていきます。

## STEP5：机が分かれているか確認する

画面の出力を見ればわかります。役割分担が動いていると、こういう表示が出ます。

```
Task(Performing task: researcherへの委譲)
Task(Performing task: writerへの委譲)
```

これが出ていれば、**別の机で実行されている証拠**です。

逆にこの表示が出ないまま会話がずっと続いている場合は、**委譲が起きていません。** 1つの机で全部やっている状態なので、STEP3の方針を見直してください。

## 設計の勘所

手順は以上ですが、ここからが差がつくところです。

### ① 3つに分けるのが基本。増やしすぎない

Anthropicが推奨しているのは、**「計画・生成・評価」の3分離**です。今回の例で言えば、調査・執筆・検証がこれにあたります。

つい「統括・企画・執筆・校閲・編集」のように細かく分けたくなりますが、**分ければ良いというものではありません。**

実践者からは、こう指摘されています。「企画」と「計画」のように**実質的に同じ思考をしている役割を分けても、トークンが2倍かかるだけで品質はほとんど変わらない**、と。

役割を増やす前に、**その2つは本当に違う思考をしているか**を確認してください。

### ② 順番に依存する作業は、並列化できない

これは当たり前のようで、見落とされます。

```
調査 → 執筆 → 検証
```

これは鎖です。調査結果がないと書けないし、原稿がないと検証できません。**どんなツールを使っても順番にしか進みません。**

並列が効くのは、**互いに独立している作業**だけです。

| 並列が効く | 効かない |
|---|---|
| 3つのテーマを同時に調査 | 調査→執筆→検証 |
| 10本の記事を同時に校閲 | 前の結果が次の入力になる作業 |
| 5つの切り口を同時に検討 | 承認を挟む手順 |

「役割分担すれば速くなる」は、**独立した作業を並べたときにだけ成立します。**

### ③ 渡す情報の設計が、実は本体

これがいちばん重要な注意点です。

**各エージェントは、これまでの会話を見ることができません。** 受け取るのは、自分の指示書と、呼び出されたときに渡された説明文だけです。

机を分けるということは、**そういうことです。** 隣の机で何が起きていたかは見えません。

```
✕「さっき調べた内容をもとに書いて」
   → 何のことか分からない

○「以下の調査結果をもとに書いて：
   ・◯◯は△△である（出典：URL）
   ・□□の数値は××（出典：URL）」
   → 動く
```

**机を分けた瞬間から、「何を渡すか」の設計が仕事の質を決めます。** ここを意識せずに使うと、分離した代わりに文脈を失って、的外れな成果物が返ってきます。

## 限界はどこか

ここまでで実用には十分ですが、正直に限界も書いておきます。

### ① エージェント同士は、直接やり取りできない

Claude Codeでは、**エージェントが別のエージェントを呼び出すことができません。** これは無限に増殖するのを防ぐための制約です。

つまり、こうなります。

```
執筆役 →（統括役に戻る）→ 検証役
```

検証役が「ここの意図は？」と執筆役に直接聞くことはできません。必ず統括役を経由します。人間の職場に例えると、**担当者同士が直接話せず、全部上司を通す組織**です。

### ② 分岐の確実性が保証されない

「検証で問題が出たら書き直させる」——これは**動きます。** 統括役が結果を読んで判断し、執筆役を呼び直します。

ただし、**必ずその通りに動く保証はありません。** 統括役が「軽微だから進めていいか」と判断してしまう可能性がゼロではないからです。

```
プログラムで書いた場合  ：条件に合えば100%その通り動く
自然言語で書いた場合    ：だいたい動くが、保証はない
```

日常的な用途では十分ですが、**絶対に飛ばしてはいけない検証がある場合は、この差が効いてきます。**

### ③ 途中で止まると、最初からやり直し

処理の状態が保存されないため、10分かかる作業が8分で中断すると、続きからは再開できません。

### 回避策——共有ファイルを「黒板」として使う

①の制約には、実用的な回避策があります。

エージェントは会話履歴を見られませんが、**ファイルは読めます。** そこで、共有のメモ置き場を作ります。

```markdown
# CLAUDE.md（追記）

## 共有メモの運用

- 各エージェントは、他のエージェントが必要とする情報だけを
  `.agent-board/` 配下のファイルに追記すること
  - researcher → `.agent-board/facts.md`
  - reviewer   → `.agent-board/findings.md`
- 呼び出す際は、読むべきファイルのパスを説明文に含めること
- 共有メモには結論と根拠だけを書く。作業の過程は書かない
```

こうすると、統括役の要約という圧縮を経由せずに、エージェント同士が情報を受け渡せます。

これは**黒板アーキテクチャ**と呼ばれる、1980年代からある古典的な設計です。教室の黒板のように、各自が必要なことだけ書き込み、必要な人が読む。近年、AIエージェントの文脈で再評価されています。

⚠️ ただし、やり取りは**一方通行**です。「ここどういう意味？」と聞いて即答をもらう、というリアルタイムの往復はできません。

## それでも足りない場合の選択肢

上の限界が問題になるなら、プログラムで組む段階です。参考までに、いずれも無料で使えます。

**コードで書く場合**

| | 向いている用途 |
|---|---|
| **CrewAI** | 役割が明確なチーム構成。20〜50行で動く |
| **LangGraph** | 複雑な業務の自動化。**途中で止まっても再開できる** |
| **AutoGen / AG2** | エージェント同士が直接やり取りする設計 |

**画面上で組む場合（プログラミング不要）**

| | 向いている用途 |
|---|---|
| **Dify** | 自分の資料を読ませたAIを、役割つきで作る |
| **n8n** | 日々の業務フローにAIを組み込む |
| **Flowise** | とりあえず動かして試す |

ただし、**どれもLLMの利用料は別途かかります。** 無料なのは仕組みの部分だけです。

## まとめ

- Claude Codeの標準機能だけで、役割分担するAIエージェントは作れる
- 必要なのは設定ファイル3枚と、運用方針1枚
- 公式推奨は3分離。増やしすぎるとコストだけ増える
- 順番に依存する作業は、そもそも並列化できない
- 机を分けたら、「何を渡すか」の設計が仕事の質を決める
- 限界は、エージェント同士が直接やり取りできないこと。共有ファイルで回避できる

そして最後に、これがこのシリーズを通していちばん伝えたかったことです。

**ここまでが、数十万円で売られている範囲です。**

技術要素で有料のものは、1つもありませんでした。設定ファイルの書き方も、3分離という設計指針も、並列実行の上限も、すべて公式ドキュメントと公開情報の中にあります。

もちろん、講座やコンサルに価値がないとは言いません。自分の業務に落とし込む伴走や、学習時間の短縮そのものに払う価値はあります。

ただ、それは**中身を知ったうえで判断すべきこと**です。「知らない」という状態のまま買うのと、「知っているが、時間を買う」ために買うのとでは、まったく違う買い物になります 👍
