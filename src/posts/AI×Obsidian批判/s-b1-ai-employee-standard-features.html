先に、いちばん都合の悪いことから書きます。

SNSやYouTubeで見かける「AI社員を作る」という情報。技術的に中身を分解した結果、そこに出てくる要素は、すべてAIツールの標準機能でした。

独自のノウハウでも、秘伝の設定でもありません。公式ドキュメントに載っている機能を、名前を変えて呼んでいるだけです。

今までに申し込もうとしている人には、受け入れがたい話だと思います。ただ、これは印象の話ではありません。順に事実を並べていきます。

「AI社員」の実体を分解する

まず、実際に何を作っているのかを見ます。

解説されている手順は、ほぼ例外なくこの2つに集約されます。

0. フォルダ📂をエディタで開けるIDE(VS Code, Antigravity IDEなど)をダウンロード
	
1. AIのCLI(Claude Code CLI, ChtaGPT CLI, Antigravity CLIなど)をダウンロード

2. CLAUDE.md というファイルを作る
   → 「あなたはSEO担当です。こういう方針で…」と書く

3. .claude/agents/ というフォルダに .mdファイルを置く
   → coder.md、designer.md のように役割ごとに1枚ずつ

以上です。 2,3は、どちらもテキストファイルで、プログラミングは必要ありません。

そして重要なのは、この2つがどちらもAIツール側が最初から用意している仕組みだという点です。特別なものを導入しているわけではありません。

海外の開発者コミュニティでは、この構成を「Role-based multi-agent（役割ベースの複数エージェント）」と呼びます。「社員」という言葉は使いません。新技術の名前ではなく、既存の仕組みに親しみやすい呼び名がついているだけということです。

指示手法は7つある

ここからが本題です。

AIに指示を与える方法は、公式に整理されているものだけで7種類あります。それぞれ「いつ読み込まれるか」が違い、その違いこそが設計の肝になります。

No. カテゴリ 手法 いつ読み込まれるか / 用途 Claude Code
1 基本設定 CLAUDE.md 開始時に読まれ、最後まで残る
常に守ってほしい方針		 CLAUDE.md
2 動的制御 Skills 呼ばれたときだけ
特定の作業手順		 ⭕
3 Hooks コンテキストの外で確実に実行
絶対に飛ばせない処理		 ⭕
4 エージェント サブエージェント 委譲時に起動し、要約を返す
役割分担		 ⭕
5 記憶・永続化 Auto Memory 毎回、自動で
過去セッションの記憶		 ⭕
6 /remember 実行したとき
繰り返しを恒久ルール化		 ⭕
7 動的制御 スラッシュコマンド 呼び出したとき

「AI社員の作り方」として説明されているのは、上から1番目と4番目だけです。

残りの5つには、ほとんど触れられていません。特にSkillsとHooksは、実務では重要度が高い機能です。

💡 なぜ「いつ読み込まれるか」が重要なのか：常に読まれるものに情報を詰め込みすぎると、AIの注意が散ります。逆に、必要なときだけ読み込む仕組みに置けば、普段は軽いまま保てます。この使い分けが、実際の精度を左右します。

記憶する仕組みは、すでに標準搭載

「AI社員」の価値として、よくこう説明されます。

普通のAIチャットは毎回ゼロから説明し直しだが、AI社員は情報が蓄積されるので、使うほど賢くなる

これは事実です。ただし、それも標準機能です。

Auto Memory——AIが自分で書く記憶

CLAUDE.md が自分の手で書くものなのに対して、Auto Memory は何も入力しなくても裏で勝手に動きます。 セッションを閉じても、次に開いたときに前回の内容を覚えています。

この仕組みの基盤は2025年後半から入っていて、画面に「記憶を思い出しました」と表示されるようになったのは2026年2月頃です。

/remember——繰り返しを恒久ルールにする

このコマンドを実行すると、AIが過去の記憶を見直して、繰り返し現れるパターンを見つけて提案してきます。

たとえば同じ指摘を3回していたら、「これは恒久的なルールにすべきでは」と持ちかけてくる。承認すれば設定ファイルに書き込まれ、以降ずっと守られます。

「使うほど賢くなる」の実装が、まさにこれです。

100万トークンの文脈保持

さらに、一度に扱える情報量も大きく増えています。現在の上限は100万トークン、日本語でおよそ75万字です。

個人が数年書き溜めたメモ程度なら、まるごと収まる規模です。

⚠️ ただし「収まること」と「ちゃんと読まれること」は別問題です。この点は別の記事で詳しく扱います。

サブエージェントは本物か

ここで疑問が浮かぶかもしれません。

.claude/agents/ に .mdファイルを置くだけで、本当に役割分担になるのか？
1つのAIが役柄を切り替えているだけではないのか？

この疑問に答えるには、まず「作業机」という考え方を押さえる必要があります。

まず、「作業机」とは何か

前の章で、AIが一度に扱える情報量には上限がある、と書きました。この「一度に見渡せる範囲」を、作業机の広さだと考えてください。

あなたがAIと会話を始めると、そのやり取りが机の上に積み上がっていきます。

質問した         → 机に載る
AIが答えた       → 机に載る
ファイルを読んだ  → その中身も机に載る
エラーが出た      → それも机に載る

会話が長引くほど、机の上は書類だらけになります。

そしてここが重要なのですが、机が散らかると、AIの精度そのものが落ちます。

AIは机の上の情報のうち、最初と最後にはよく反応するのに、真ん中に埋もれたものを見落としやすいという性質があるからです。長い会議の冒頭と結論だけ覚えていて、中盤を忘れてしまう感覚に近いものです。

💡 だから「机をきれいに保つ」ことが、そのまま精度を保つことになります。

「親」とは、誰のことか

ここで、用語を1つ整理します。

あなたがAIを起動して、実際に話しかけている相手。この最初の1体を「親」と呼びます。

あなた
  ↓ 話しかける
【親】 ← あなたが直接やり取りする相手。全体を見ている
  ↓ 仕事を振る
【サブエージェント】 ← 特定の作業だけを任される

会社でたとえるなら、親は窓口の担当者です。あなたの要望を聞いて、必要なら専門の担当者に振り分ける。そして結果をまとめて、あなたに返す。

あなたが会話しているのは、常に親だけです。 サブエージェントと直接話すことはありません。

「役柄の切り替え」だと、何が起きるか

では本題です。

「今はデザイナーとして考えて」「次はコーダーとして書いて」と指示を切り替える方式だと、どうなるでしょうか。

【親の机】
├── デザイナーとして考えた内容
├── 途中でやめた案
├── コーダーとして書いたコード
├── 動かなかった試行錯誤
└── チェック役としての指摘

全部、同じ机の上に積み上がります。

これは役割分担ではありません。1人のAIが、同じ机の前で服を着替えているだけです。机はどんどん散らかり、さきほどの「真ん中を見落とす」現象が起きやすくなります。

サブエージェントは、机ごと分かれている

一方、サブエージェントを使うとこうなります。

【親の机】
└── 「実装完了。3ファイル変更しました」 ← これだけ

【コーダーの机】（別の場所にある）
├── 仕様を読んだ
├── 1000行書いた
├── エラーが出た
├── 直した
└── 完成 → 要約だけを親に渡して、机ごと片付く

ここが決定的な性質です。

サブエージェントは、作業の過程を親に見せません。要約だけを返します。

コーダー役が1000行書いて試行錯誤しても、親の机に届くのは「実装完了」の1行だけ。 途中の失敗も、消した案も、親の机には乗りません。

これは役柄の切り替えでは、絶対に実現できません。 切り替えなら、試行錯誤が全部同じ机に残ってしまうからです。

💡 つまり「机が分かれていること」が、本物の役割分担である証明になっています。 ここは、商材の説明どおりに正しく機能します。

ただし、置くだけでは動かない

ここが、この記事でいちばん実用的な部分かもしれません。

ファイルを置くだけでは、役割分担は発動しません。

明示的に「この作業は誰に任せろ」と指示しない限り、AIは自分でやってしまいます。 「わざわざ人を呼ぶより自分でやったほうが早い」と判断するからです。

❌ .claude/agents/coder.md を置いただけ
   → 親が自分で実装してしまう
   → 机が1つのまま。分担していない

⭕ CLAUDE.md に「実装は必ず coder に委譲すること」と明記
   → 初めて机が分かれる

ここに触れている解説を、僕はあまり見かけません。

「.mdファイルを置けばAI社員の完成」と説明されていると、読者は分かれていない状態を「分かれている」と思い込んだまま使い続けることになります。

💡 確認方法：画面に「Task(委譲中...)」のような表示が出ていれば、実際に分担が起きています。出ないまま会話が続いている場合は、1つの机で全部やっている状態です。

では、「AI社員」で教えられているのは、どちらなのか

ここで、整理しておきたいことがあります。

「AI社員」と呼ばれているものには、実は2つのパターンがあります。見た目は似ていますが、中身がまったく違います。

パターン① パターン②
やり方 役割ファイルを置き、
委譲を明記する		 指示書に
「あなたは◯◯です」と書く
机 役割ごとに分かれる 1つのまま
実態 本物の役割分担 役柄の切り替え
並列実行 できる できない

パターン①が、本来イメージされている「AI社員」です。

あなた
  ↓
【オーケストレーター】＝ メインエージェント
  ↓ 仕事を振る
【デザイナー】【コーダー】【チェック役】← サブエージェント
  → それぞれ別の机で働き、要約だけを返す

会社の組織図そのままです。これが成立していれば、「AI社員」という呼び方は妥当です。

ところが、公開されている手順を見ると

ここからが本題です。

「AI社員の作り方」として公開されている手順を確認すると、多くがパターン②でした。

典型的な流れはこうです。

① フォルダを作る
② 資料を入れる
③ 指示書ファイルに「あなたは◯◯担当です」と書く
④ AIに読ませる

役割ファイルを別に置く工程も、委譲を指示する工程も、出てきません。

つまり——

役割は与えているが、机は1つのまま。
組織ではなく、1人が服を着替えているだけの状態です。

⚠️ もちろん、すべてがそうだと断定はできません。 公開されていない部分でパターン①を扱っている可能性もあります。ここで言えるのは「公開されている手順の範囲では、②が多い」という事実だけです。

問題は、買う側が①だと思っていること

「AI社員」「チームを組む」「並列で動く」——こういった言葉から想像するのは、間違いなくパターン①です。

ですが②では、並列実行はできません。 机が1つしかないので、順番にしか進みません。

そして会話が長引くほど机は散らかり、前の章で説明した「真ん中を見落とす」現象が起きやすくなります。

💡 だから、この記事でいちばん実用的なのは前の節です。 委譲を明記しているかどうか。画面に委譲の表示が出ているかどうか。この2点を確認するだけで、①なのか②なのかが分かります。

おまけ：無料のほうが正しい構造になる場合がある

ここは少し皮肉な話です。

次回の記事で、Pythonを20行ほど書いて役割分担を再現します。そのとき、机は自動的に分かれます。

理由は単純で、AIを呼び出す仕組みが、前回のやり取りを覚えていないからです。呼ぶたびに机がまっさらになります。

つまり——

無料で書ける20行のほうが、パターン②より構造的に正しいということが起こりえます。

それを確かめるのが、次回の内容です。

これはClaude Code固有の話ではない

ここまでClaude Codeを例に説明してきました。では他社ではどうなのか。

調べた結果、3社ともほぼ同じ機能セットに収束していました。

役割分担も、記憶も、スキルも、どこか1社の特別な機能ではありません。 2026年時点の業界標準です。

ちなみにOpenAIのものは、記憶の実装がかなり凝っています。作業フォルダごとに記憶を出し分けたり、古くなった情報を自動で忘れたり、よく使う記憶を優先したりという処理まで入っています。

逆に意外だったのがGoogleです。Antigravity CLIには、セッションを跨ぐ記憶が標準では入っていません。 毎回ゼロから説明し直しが既定の動作で、記憶が欲しければ外部の仕組みを繋ぐ必要があります。

つまり——「AI社員」という言葉で売られている機能は、どの会社を選んでも、契約すれば最初から付いてきます。

3社それぞれの、役割の作り方

せっかくなので、実際にどう書くのかを3社分まとめておきます。

置き場所とファイル形式が違うだけで、やることは同じです。

ツール ファイル形式 置き場所（プロジェクト用）
Claude Code Markdown ＋ YAML .claude/agents/
Codex CLI TOML .codex/agents/
Antigravity CLI Markdown ＋ YAML .agents/agents/

▸ Claude Code

Markdownファイルの先頭に設定を書き、その下に指示文を書きます。

.claude/agents/reviewer.md
---
name: reviewer
description: コードレビュー担当。実装が終わったら必ず使う
tools: Read, Grep
---
あなたはコードレビュアーです。
問題があれば該当箇所と理由をセットで指摘してください。
コードは書かないでください。

▸ Codex CLI

こちらだけTOML形式です。書き方は違いますが、指定する内容はほぼ同じです。

.codex/agents/reviewer.toml

name = "reviewer"
description = "コードレビュー担当。実装が終わったら必ず使う"
model = "gpt-5.4"
sandbox_mode = "read-only"
developer_instructions = """
あなたはコードレビュアーです。
問題があれば該当箇所と理由をセットで指摘してください。
コードは書かないでください。
"""

💡 Codexには最初から3つの役割が用意されています。 default（汎用）、worker（実装担当）、explorer（調査担当）。自分で作らなくても、この3つはすぐ使えます。

▸ Antigravity CLI

Claude Codeとほぼ同じ形式です。ただし1つだけ、他にはない特徴があります。

.agents/agents/reviewer.md
---
name: reviewer
description: コードレビュー担当
tools:
  - view_file
  - grep_search
subagent: true
mainAgent: true
model: pro
---
# システムプロンプト
あなたはコードレビュアーです。
問題があれば該当箇所と理由をセットで指摘してください。

注目してほしいのは、この2行です。

subagent: true    ← サブとして呼べる
mainAgent: true   ← メインとしても起動できる

同じ定義ファイルが、「呼ばれる側」にも「話しかける相手」にもなれます。

他社では、自分で作った役割はサブとしてしか使えません。 あなたが直接話しかける相手は、常に標準のメインエージェントです。

Antigravityでは、起動時に「今日はレビュアーと話す」と指定できます。 実際、公式もこれを他社との違いとして挙げています。

3社に共通する、いちばん大事な注意点

どのツールでも、ファイルを置いただけでは起動しません。

Codexの公式ドキュメントにも「ファイルが存在するだけでは自動的に起動しない」と明記されています。明示的に頼むか、指示書ファイルに委譲のルールを書く必要があります。

💡 これは前の章で書いた内容と同じです。 会社が変わっても、この落とし穴は共通です。

まとめ

  • 「AI社員」の実体は、CLAUDE.md と .claude/agents/ の .mdファイル

  • 役割分担は本物。ただし委譲を明記しないと発動しない
