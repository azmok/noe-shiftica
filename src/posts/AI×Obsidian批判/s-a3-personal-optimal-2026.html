ここまでで、Obsidianの限界も、Vector・Graph・GraphRAGの仕組みも押さえました。

残る問いは1つです。「で、自分は結局どうすればいいのか」

結論を先に書きます。

多くの人は、まだ何もしなくていいです。

そして、やるべきタイミングが来たときも、最も高機能な選択肢が最も適切であることは、まずありません。 順番に説明します。

判断基準は「蓄積量」だけです

技術の話に入る前に、いちばん実用的な判断表を置いておきます。

段階蓄積量の目安やるべきこと
第1段階〜数百ノート索引の仕組みを作る。設定は数行で済む
第2段階数百〜数千意味で探す仕組みだけを追加する
第3段階数千以上つながりの自動抽出を検討する

多くの個人は、第1段階か第2段階のどこかにいます。第3段階まで行く人は、かなり限られます。

第1段階：作り込む必要はない。ただしゼロでもない

ここが最も重要な段階です。

数百ノート程度なら、検索の仕組みを自分で作り込む必要はありません。 この段階でデータベースを構築するのは、目的と手段の逆転です。

ただし、やることがゼロというわけでもありません。

正確に言うと、こうなります。

「索引の仕組み」だけは用意する。ただし設定は数行で済む。

そして——この「数行」の中身が、チャットで使っているか、ターミナルで使っているかで変わります。 後半で分けて説明します。

前回紹介した事例が、そのまま根拠になります。約100記事・40万語の規模で「凝った検索の仕組みは不要だった」という報告がありました。

規模が小さいうちは、シンプルな構成が正解です。

実例：Karpathy氏の「LLM Wiki」

この事例は、2026年4月に本人が具体的な設計として公開しています。よくできているので、簡単に紹介します。

構成は、3つのフォルダだけです。

raw/       ← 元の資料をそのまま置く（追記のみ。編集しない）
wiki/      ← AIが書いた、整理済みのページ
agents.md  ← AIへの指示書

やっていることは、こうです。

  1. raw/ に資料を放り込む（PDF、記事、議事録、何でも）
  2. AIがそれを読んで、wiki/ に整理したページを書く
  3. AIがページ同士のリンクも自動で張る
  4. AIが「索引ファイル」を更新する（全ページの一覧＋一行要約）

そして質問するときは——AIはまず索引を読み、必要なページだけを開きます。

ここが肝です。毎回すべてを検索するのではなく、あらかじめ整理された結果を読む。 ある解説はこれを「検索エンジンではなく、知識のコンパイラ」と表現していました。

📌 注目してほしい点が1つあります。

リンクを張っているのは人間ではなく、AIです。

Obsidianは、そのリンクを図で見るために使われているだけ。Karpathy氏自身も「必須ではない」としています。

つまりこれは、前回の記事で書いた「書く層」と「活かす層」を分けた構成そのものです。Obsidianは見るための道具で、活かす層はAIが担当しています。

この方式が壊れるのは、いつか

限界も、はっきりしています。

ファイル数がおよそ200件を超えると、索引が大きくなりすぎて、AIが全体を保持できなくなる

対処は2つあります。

  1. 索引を階層化する（フォルダごとに索引を作る）→ 数百件までは延命できます
  2. それでも足りなくなったら → 意味で探す仕組み（第2段階）へ

「数百ノート」とは、どのくらいの量か

具体的な数字にしてみます。前回紹介した事例を日本語に換算すると、こうなります。

項目数値
ファイル数約100件
総量（英語）40万語
日本語に換算すると約80万〜100万文字
1件あたり約8,000〜10,000文字

1件あたりがかなり長いことに気づくと思います。研究用のまとめなので、1件が長めのブログ記事くらいの分量です。

そして、ここが重要な点です。

基準になるのは、総文字数ではなくファイル数です。

理由はシンプルで、索引を使う方式では開くのは必要なファイルだけだからです。総量が100万文字あっても、索引を見て3件だけ開けば済むなら、残りの97万文字は読まれません。

だから、こう考えてください。

1件あたり300件のときの総量索引方式で回るか
500文字（短いメモ）15万文字⭕
2,000文字（調べ物メモ）60万文字⭕
8,000文字（長文記事）240万文字⭕

総量がどれだけ大きくても、ファイル数が索引に収まれば機能します。

逆に言えば、限界が来るのはファイル数のほうです。1行1件の索引なら、300〜500行あたりが読みやすさの上限でしょう。それを超えると、索引そのものが読めなくなります。

💡 第1段階の目安は「300件程度まで」。 1件が短いメモでも、長文記事でも、判断は変わりません。

【チャットで使っている方】索引は不要です

まず、ブラウザやアプリのチャット画面だけを使っている方。

結論から言うと、索引ファイルを作る必要はありません。

理由は、各社のプロジェクト機能に、すでに検索の仕組みが入っているからです。

やることは1つだけ。資料をプロジェクトに入れる。それだけです。

サービス機能名中の動き
ChatGPTプロジェクト／GPTs最初から検索方式（関連部分だけを引く）
Claudeプロジェクトまず全部読む。増えたら自動で検索方式に切り替わる
GeminiGem検索方式

Claudeの挙動が特に分かりやすいです。入れた資料が一定量を超えると、自動的に「全部読む」から「必要な部分だけ引く」へ切り替わります。 利用者は何も設定しなくて済みます。

⚠️ ただし、上限が早く来ます。

サービスファイル数の目安
Gemini（Gem）10ファイルまで
ChatGPT（GPTs）20ファイルまで
Claude（プロジェクト）件数の制限はないが、容量に実質的な上限あり

数字を見てのとおり、「数百ノート」に到達する前に、上限のほうが先に来ます。

💡 チャットだけで使う場合、第1段階は「プロジェクトに入れるだけ」で完了です。 ファイルが増えてきたら、まとめたり整理したりが必要になります。

⚠️ そしてもう1つ大事な点。チャットのAIは、あなたのファイルを書き換えられません。 索引を作っても、更新はあなたの手作業になります。ここが、次の話との決定的な差です。

【ターミナルで使っている方】索引システムを作る価値があります

Claude Code CLI、Codex CLI、Antigravity CLIなど、ターミナルから使うAIツールを導入している方。こちらは事情がまったく違います。

決定的な差はここです。

AIが、あなたのファイルを直接読み書きできます。

つまり——索引ファイルを、AIに自動で維持させられます。 手作業になりません。

セットアップ：プロンプト1つで完了します

作業フォルダでAIを起動し、次の文章を貼り付けてください。ファイルがまだ存在しなくても大丈夫です。作るところからやってくれます。

このプロジェクトに、記録を蓄積するための索引システムを作ってください。
まだ何も存在しない状態からのセットアップです。

できあがる索引ファイル

こういう形のものが、自動で維持されるようになります。

# 索引

- `2026-07-01-配色の方針.md` — 落ち着いた配色に統一すると決めた経緯
- `2026-07-08-スマホ対応.md` — 横スクロールが出る問題と対処
- `2026-07-15-競合調査.md` — 同ジャンル5サイトの構成比較

AIは作業のたびにこの索引を読み、必要なファイルだけを開きます。 全部読むわけではないので、量が増えても重くなりません。

💡 更新が気になる場合は、1日1回「今日の記録を索引に反映して」と頼むだけでも十分です。

組み合わせると効く、3つの道具

ターミナル版には、無料で使える道具が3つあります。性質が違うので、揃うと強くなります。

道具得意なこと費用
キーワード検索書いた言葉を覚えているとき、最速ゼロ
自動記憶（標準搭載）直近の作業の文脈を引き継ぐゼロ
索引ファイル全体を俯瞰し、必要な場所へ案内するほぼゼロ

⚠️ 1つ注意点があります。 自動記憶は、Claude Code CLIとCodex CLIには標準で入っていますが、Antigravity CLIには入っていません。 Antigravity CLIを使う場合、索引ファイルの重要度が上がります。

⚠️ そして、この方式の限界は1つだけ。意味では探せません。 索引に書かれた説明文から推測するだけなので、まったく違う言葉で書かれた記録は見つかりません。それが頻発し始めたら、第2段階です。

第2段階：意味で探す仕組みだけを追加する

「あのノート、何と書いたか思い出せない」が頻発し始めたら、この段階です。

追加するのはVector検索だけで十分です。 つながりの自動抽出（Graph）は、まだ要りません。

理由は、個人の使い方の大半が「あの話、どこかに書いたはず」という意味での検索だからです。「Aから3手先にある関係」を探す場面は、実際にはあまり訪れません。

第3段階：つながりの自動抽出を検討する

数千ノートを超えて、かつ「つながりを発見したい」という明確な目的があるときだけ、Graphを足す価値が出ます。

「検討する」と書いたのは、この段階でも必須ではないからです。次のコストの話が効いてきます。

なぜ段階を分ける必要があるのか

理由は2つあります。1つは精度、もう1つはコストです。

理由①：入りきることと、読まれることは別問題

前回触れたLost in the Middle（中抜け）を、もう少し正確に説明します。

AIは渡された情報のうち、最初と最後には強く反応しますが、真ん中に埋もれた情報を見落としやすいという性質を持っています。これは注意の仕組みそのものに組み込まれた偏りで、2026年時点でも構造的には解消されていません。

ここが誤解されやすいポイントです。

AIが一度に扱える量が増えた
　　≠
渡したもの全部を、均等に読んでくれる

つまり、「全部読ませればいい」という発想そのものが成立しません。 数千ノートが仮に収まったとしても、真ん中は見落とされます。

だからこそ、質問に関係するものだけを事前に絞り込んで渡す必要がある。これがVector検索を入れる本当の理由です。

理由②：純正のGraphRAGは、個人には確実に過剰

前回、GraphRAGはMicrosoft Researchが2024年に発表した手法だと紹介しました。ただし、そのまま導入するのは個人にはまったく勧められません。コストが桁違いだからです。

初期の実装では、大規模なデータセットの処理に3.3万ドルかかったという報告があります。32,000語程度の書籍1冊でも、約7ドル。

前回説明したとおり、費用の主犯はAIを呼び出す工程です。そして純正のGraphRAGは、その高コストな工程を全部、事前に一括で実行する設計になっています。

継続的に増えていく用途との相性

個人にとって、さらに相性が悪い点があります。

GraphRAGはデータ全体を作り直す前提なので、毎日ノートが増える使い方だと、更新のたびに重い再構築が発生しやすくなります。

Microsoft自身もこの問題を認識していて、2025年にはLazyGraphRAG（重い処理を、質問が来るまで先送りする手法）を発表しています。外部からもLightRAG（追加分だけを処理できる手法）が登場し、コストを大幅に圧縮しています。

「純正GraphRAGは重すぎる」というのが、すでに共通認識になっているということです。

個人が採るべきは、「保存したときに、そのノートだけを処理する」という追加分だけの方式です。これなら費用は使った分だけで済みます。

技術選定——ファイル1つで完結する

第2段階以降に進む場合、何を使うか。個人スケールなら答えは単純です。

SQLite（データベース本体）
  ＋ sqlite-vec（意味検索の拡張機能）
  ＝ 単一ファイルで完結

大がかりなデータベースサーバーは要りません。ファイル1つで動きます。

しかも、これは前々回の話と綺麗につながります。SQLiteのファイル形式は米国議会図書館の長期保存推奨形式で、2050年までのサポートが宣言されています。

Markdownと同等の永続性を持ったまま、検索の仕組みだけを手に入れられるわけです。

全体の構成

【保存層】 SQLite + sqlite-vec
          ノートの原文と、意味の座標を1ファイルに格納

【処理層】 ノートを保存したとき、そのノートだけを処理
          → 意味の座標を計算
          → 既存ノートとの関係候補を算出
          → つながりとして追記

【検索層】 意味検索 ＋ キーワード検索を組み合わせる
          （第3段階なら、ここに関係の探索を足す）

ポイントは、原文をデータベースの中に持つことです。こうしておけば、AIモデルが世代交代して座標が古くなっても、原文から作り直せます。壊れやすい部分を使い捨てにできる設計です。

実装の落とし穴3つ

自分で作る場合、必ずぶつかる課題があります。知らずに始めると確実に手戻りします。

① つながりの判定基準

意味の近さでつながりを自動生成するとき、基準の設定が要ります。緩すぎれば全部がつながって読めなくなり、厳しすぎれば孤立したノートだらけになります。

堅実なのは二段構えです。まず意味の近さで候補を出し、次にAIに関係の内容を判定させて絞り込む。この2段階にすると、精度が安定します。

② 表記のゆれ

「田中太郎」「田中さん」「タナカ」が、別々のものとして登録されてしまう問題です。

個人のノートでは、同じ人や同じプロジェクトを気分で呼び分けていることが普通にあります。同一のものとしてまとめる処理を、最初から設計に入れてください。

③ 表示位置の連続性

つながりを図で表示する場合の注意点です。

絞り込みをかけるたびに配置が作り直されると、「あのかたまりは左上にあった」という空間的な記憶がリセットされます。 図で見る利点そのものが消えてしまうんです。

位置は保存しておき、絞り込み時は差分だけを動かす設計にしてください。

今日から動かせる実装プロンプト

AIコーディングエージェント（Claude Code CLIやAntigravity CLIなど）に渡すだけで、試作品の構築が始まるプロンプトを置いておきます。上の落とし穴3つへの対策も、あらかじめ組み込んであります。

Build a local-first personal knowledge base prototype.

## Stack
- Backend: Node.js + SQLite (better-sqlite3) with the sqlite-vec extension
  — single file, no database server
- Frontend: React + React Flow (graph canvas) + a Markdown editor pane
- Embeddings: pluggable provider interface — assume an embed(text) -> float[]
  function; stub it so I can swap in a local model or an API

## Data model
- notes(id INTEGER PRIMARY KEY, title TEXT, body TEXT, created_at, updated_at)
- embeddings(note_id, vector) — one per note, always regenerable from body
- edges(from_id, to_id, weight REAL, label TEXT,
        source TEXT CHECK(source IN ('auto','manual')))
- entities(id, canonical_name, aliases TEXT[]) — for name normalization
- node_positions(note_id, x REAL, y REAL)
All relations use integer IDs. Titles are display-only, never keys.

## Core behaviors
1. Incremental indexing on save: re-embed ONLY the saved note, compute
   candidate edges against existing notes via cosine similarity
   (threshold as a config constant, default 0.78), then pass the top
   candidates to an LLM to assign a relationship label and prune
   false positives. Upsert with source='auto'. Never delete manual edges.
2. Entity normalization: before creating a node, check the entities table
   for an alias match. Merge instead of creating duplicates.
3. Search API: hybrid retrieval — vector similarity + keyword (FTS5),
   merged and re-ranked. Return only the top N chunks, never whole files.
4. Graph API: GET /graph?root={id}&hops={n}&from={date}&to={date}
   returns the filtered subgraph using a recursive query over edges.
5. Frontend layout: run force-directed layout ON FIRST RENDER ONLY.
   Persist positions to node_positions. On filter change, animate the
   enter/exit of nodes — never recompute positions of surviving nodes.
6. Include a "reindex all" command that regenerates every embedding and all
   auto edges from source text, proving the analysis layer is disposable.

## Constraints
- Single repo, npm scripts for dev/run
- Seed with 30 sample notes across 3 topics so the graph is demoable
- README documenting the similarity threshold and how to tune it

Confirm the schema with me before implementing the frontend.

💡 第2段階までで十分な人は、4と5のグラフ関連を外してください。 それだけで、意味検索だけのシンプルな構成になります。

全体像——どこまで行くと、何が必要になるか

ここまでの話を、1枚にまとめます。

段階やること目安費用
第0段階AIツールの標準機能を有効にする常にゼロ
第1段階＋ 索引ファイル方式〜200件ほぼゼロ
第1.5段階＋ 索引の階層化〜数百件ほぼゼロ
第2段階＋ 意味で探す仕組み（Vector）数百〜数千件座標化の費用
第3段階＋ つながりの自動抽出（Graph）数千件〜高い

下に行くほど強力になりますが、同時に「作る手間」と「壊れたときの責任」も増えます。

よくある誤解——フレームワークは、この表の続きではない

「もっと本格的なフレームワークを導入すれば、さらに賢くなるのでは」と考える方もいると思います。

ですが、それは別の軸の道具です。

【この表の軸】検索・想起の精度を上げる
              索引 → Vector → Graph

【フレームワークの軸】自動で動き続ける・自分で学習する
