最終回です。

前回、素のPythonの限界は「道具の数ではなく、管理」にあると分かりました。権限、リトライ、記録、再開——ここが重くなる。

今回は、その部分を引き受けてくれるフレームワークを入れます。そして素で書いたものと並べて、何が変わったのかを確かめます。

今回やること

  1. CrewAIで、同じ5人チームを書き直す
  2. 素のPython版と比較して、何が消えて何が増えたかを見る
  3. ブラウザ確認を組み込む
  4. かかったコストを実測する

大事なのは、比較のために先に素で書いておいたという点です。いきなりフレームワークから始めていたら、何を代わりにやってもらっているのか分からないままでした。

CrewAIを導入する

uv add crewai crewai-tools

APIキーは、これまでと同じ .env の GEMINI_API_KEY をそのまま使えます。

CrewAIの構成要素は4つだけです。

用語意味
Agentチームの一員。役割・目標・経歴・使える道具を持つ
Task仕事。何をするかと、何を出すかを書く
Crewチーム。誰と誰で、どのタスクをこなすか
Process進め方。順番どおり（sequential）か、統括が振り分ける（hierarchical）か

ここまでの記事で作ってきたものと、対応関係がはっきりしています。

これまでの roles.py の文字列 → Agent の role / goal / backstory
これまでの main.py の呼び出し → Task
これまでの main() 関数全体    → Crew + Process

同じチームを、CrewAIで書き直す

import os
from pathlib import Path

from crewai import Agent, Task, Crew, Process
from crewai.tools import tool
from dotenv import load_dotenv

load_dotenv()

SMART = "gemini/gemini-2.5-pro"
FAST = "gemini/gemini-2.5-flash"

THEME = "海の見える個人経営のカフェ。落ち着いた大人向けの雰囲気"


# ---- 道具 ----
@tool("ファイル保存")
def write_file(path: str, content: str) -> str:
    """指定されたパスにファイルを保存する。

    Args:
        path: 保存先のパス（例: output/index.html）
        content: 書き込む内容
    """
    p = Path(path)
    p.parent.mkdir(parents=True, exist_ok=True)
    p.write_text(content, encoding="utf-8")
    return f"{path} に保存しました"


# ---- チーム ----
researcher = Agent(
    role="リサーチャー",
    goal="テーマに関する事実と傾向を、5項目以内で整理する",
    backstory="一次情報を重視し、推測と事実を厳密に区別する。意見は述べない",
    llm=FAST,
    allow_delegation=False,
)

designer = Agent(
    role="UIデザイナー",
    goal="実装可能なWebページの仕様を決める",
    backstory="構成・配色・文言を具体的に決めるが、コードは書かない",
    llm=SMART,
    allow_delegation=False,
)

coder = Agent(
    role="フロントエンドエンジニア",
    goal="仕様どおりの1枚のHTMLを実装し、ファイルに保存する",
    backstory="外部ファイルに依存しない実装を好む。仕様にないものは足さない",
    llm=SMART,
    tools=[write_file],
    allow_delegation=False,
)

reviewer = Agent(
    role="QAエンジニア",
    goal="仕様と実装の食い違いを見つける",
    backstory="「動く」ではなく「仕様どおりか」を基準にする。自分では直さない",
    llm=FAST,
    allow_delegation=False,
)


# ---- 仕事 ----
research_task = Task(
    description=f"次のテーマについて調べてください：{THEME}",
    expected_output="事実と傾向の箇条書き（5項目以内）",
    agent=researcher,
)

design_task = Task(
    description="調査結果をもとに、1枚のWebページの仕様を作ってください",
    expected_output="構成・配色（カラーコード）・各セクションの文言を含む仕様書",
    agent=designer,
    context=[research_task],
)

code_task = Task(
    description=(
        "仕様どおりのHTMLを実装し、write_file で output/index.html に保存してください"
    ),
    expected_output="保存したファイルのパス",
    agent=coder,
    context=[design_task],
)

review_task = Task(
    description=(
        "仕様と実装を照合してください。"
        "問題がなければ1行目に PASS、あれば FAIL と書き、指摘を列挙してください"
    ),
    expected_output="PASS または FAIL と、指摘の一覧",
    agent=reviewer,
    context=[design_task, code_task],
)


# ---- 実行 ----
crew = Crew(
    agents=[researcher, designer, coder, reviewer],
    tasks=[research_task, design_task, code_task, review_task],
    process=Process.sequential,
    verbose=True,
)

if __name__ == "__main__":
    result = crew.kickoff()
    print(result)

⚠️ allow_delegation=False は重要です。 これを True にすると、担当者同士が延々と仕事を押し付け合って止まらなくなることがあります。委譲を許すのは統括役だけにしてください。

Before / After——何が変わったか

消えたもの

素のPython版CrewAI版
for attempt in range(...) の差し戻しループCrewが管理
ThreadPoolExecutor での並列化async_execution=True の指定だけ
extract_code() でコードフェンス除去道具で直接保存するので不要
print() での進行表示verbose=True
前工程の出力を手で埋め込む処理context=[...] の指定だけ

残ったのは、役割の定義と仕事の定義だけです。 管理のためのコードが、ほぼ全部消えました。

特に context=[design_task] は象徴的です。素のPythonでは、こう書いていました。

f"以下の仕様を実装してください：\n\n{design}"

「前の出力を、次の指示文に埋め込む」——この手作業が、1つの引数に置き換わっています。

増えたもの

いいことばかりではありません。正直に書きます。

  1. 何が起きているか見えなくなる——AIに実際どんな文章が送られているのか、コードから読み取れません
  2. 依存パッケージが一気に増える——インストールに時間がかかり、バージョンの衝突も起きやすくなります
  3. デバッグが難しくなる——うまくいかないとき、自分のコードなのかフレームワーク側なのか切り分けが要ります
  4. フレームワークの作法を覚える必要がある——context、expected_output、allow_delegation……独自の概念が増えます

ここで、このシリーズを素のPythonから始めた理由がはっきりします。

先に手で書いたから、抽象化の下で何が起きているか読める。
いきなりCrewAIから始めていたら、context=[...] が「前の出力を指示文に埋め込む処理」だと知らないまま使っていたはずです。

そして問題が起きたとき、この差が効きます。中身を知っていれば、フレームワークを疑うことも、外して確かめることもできます。

ブラウザで本当に確認させる

前回、検証役の課題として残していた部分です。コードを読むだけでなく、実際にブラウザで開いて確認させたい。

方法は2つあります。

① 自分で組む

uv add playwright
uv run playwright install chromium
from playwright.sync_api import sync_playwright


@tool("画面を撮影")
def screenshot(path: str, width: int = 375) -> str:
    """HTMLファイルをブラウザで開いてスクリーンショットを撮る。

    Args:
        path: HTMLファイルのパス
        width: 画面の横幅（375ならスマホ相当）
    """
    out = f"output/shot_{width}.png"
    with sync_playwright() as p:
        browser = p.chromium.launch()
        page = browser.new_page(viewport={"width": width, "height": 800})
        page.goto(f"file://{Path(path).resolve()}")
        page.screenshot(path=out, full_page=True)
        browser.close()
    return f"{out} に保存しました"

⚠️ ただし、これだけでは半分です。撮った画像をAIに見せる処理が別途必要になります。テキストと画像では渡し方が違うためです。

② Antigravityのブラウザ機能を使う

Antigravityには、ブラウザを操作するエージェントが標準で組み込まれています。実際にChromeでページを開いて確認し、その操作が記録として残ります。

つまり、Pythonのコードで完結させずに、最終確認だけAntigravity側に任せるという分担もありえます。

output/index.html をブラウザで開いて、次を確認してください。

- スマホ幅（375px）で横スクロールが発生しないか
- 各セクションが仕様どおりの順番で並んでいるか
- 文字が背景に埋もれて読めない箇所がないか

問題があれば、該当箇所と修正案を教えてください。

全部を自動化しなくていい、という判断もあります。最終確認だけ人間の目と対話で済ませるほうが、確実で早い場面は多いです。

コストを実測する

「結局いくらかかるのか」は、実際に測るのが一番確実です。推測より計測です。

素のPython版なら、応答に含まれるトークン数を記録できます。

TOTAL = {"in": 0, "out": 0}


def agent(role: str, task: str, model: str = "gemini-2.5-flash") -> str:
    res = client.models.generate_content(
        model=model,
        config=types.GenerateContentConfig(system_instruction=role),
        contents=task,
    )
    u = res.usage_metadata
    TOTAL["in"] += u.prompt_token_count
    TOTAL["out"] += u.candidates_token_count
    return res.text


# 実行の最後に
print(f"入力: {TOTAL['in']:,} トークン / 出力: {TOTAL['out']:,} トークン")

CrewAIの場合は、実行結果からまとめて取得できます。

result = crew.kickoff()
print(result.token_usage)

あとは公式の料金表で単価を確認して、掛け算するだけです。

費用 = (入力トークン ÷ 100万 × 入力単価)
     + (出力トークン ÷ 100万 × 出力単価)

💡 実測すると、たいてい予想より安いか、予想より高いかのどちらかで驚きます。 特に差し戻しが何度も起きると、そこで一気に増えます。無料枠の範囲で試す場合も、まず測る習慣をつけておくと安心です。

検証——どこまでできて、どこが限界か

ここは、実際に動かして確かめる部分です。誇張せずに評価するための観点を置いておきます。

観点見るポイント
仕様の再現度design.md に書かれたセクションが、全部実装されているか
配色の一致指定されたカラーコードが、実際に使われているか
レスポンシブ375px幅で横スクロールが出ないか
検証役の精度指摘が的確だったか。見逃した問題はなかったか
差し戻しの効果1回目と2回目で、実際に良くなったか
実用度そのまま公開できるか。手直しが要るなら、どの程度か

特に注目してほしいのが「検証役が見逃した問題」です。ここに、この構成の限界がそのまま現れます。

まとめ——シリーズ全体を振り返って

4回かけて作ってきたものを、圧縮します。

  • 第1回：役割の正体は、system promptに渡すただの文字列。中核は15行の関数
  • 第2回：品質を決めるのは検証役。判定を PASS/FAIL にすると、プログラムが確実に分岐できる
  • 第3回：道具を持たせるのは簡単。難しいのは、増えたときの管理
  • 第4回：フレームワークは管理を引き受ける代わりに、中身を隠す

そして、シリーズ全体で使った費用はAPIのトークン代だけです。

CrewAIもLangGraphも無料のオープンソースです。Antigravityにも無料枠があります。Ollamaを使えば、モデルの利用料すらゼロにできます。

技術要素で有料のものは、1つもありませんでした。

もちろん、講座やコンサルに価値がないとは言いません。自分の業務に落とし込む伴走や、学習時間の短縮そのものに払う価値はあります。

ただ、それは中身を知ったうえで判断すべきことです。「知らない」まま買うのと、「知っているが時間を買う」ために買うのとでは、まったく違う買い物になります。
