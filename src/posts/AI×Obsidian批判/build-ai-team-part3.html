前回、5人チームを動かしました。ただし正直に書いたとおり、大きな制限が残っています。

リサーチャーは、実際には何も調べていません。 AIがもともと知っていることを整理しているだけです。

今回は、そこを解決します。AIに「道具」を持たせる——専門用語ではツール使用（function calling）と呼ばれる仕組みです。

前回残した宿題

やらせたいことは3つあります。

誰に何を今の状態
リサーチャー本当にWebを検索する知識だけで答えている
コーダーファイルを自分で書く文字列を返すだけ
検証役ブラウザで実際の表示を見るコードを読んでいるだけ

先に結論を書くと、①と②は驚くほど簡単に解決します。 ③だけが、本当に面倒です。

そして「じゃあ何が限界なのか」という問いの答えは、道具そのものではないところにありました。

道具を持たせてみる

① Web検索——組み込みで解決する

これは自分で実装する必要がありません。検索機能が最初から用意されています。

from google import genai
from google.genai import types

client = genai.Client()


def agent_with_search(role: str, task: str, model: str = "gemini-2.5-flash") -> str:
    res = client.models.generate_content(
        model=model,
        contents=task,
        config=types.GenerateContentConfig(
            system_instruction=role,
            tools=[types.Tool(google_search=types.GoogleSearch())],
        ),
    )
    return res.text

追加したのは tools= の1行だけです。

これでリサーチャーは、必要だと判断したときに自分で検索し、その結果を踏まえて答えるようになります。検索するかどうかも、何を検索するかも、AIが決めます。

前回の役割定義も、あわせて更新しておきます。

RESEARCHER = """あなたはリサーチャーです。
渡されたテーマと観点について、Webで調べて要点を整理してください。

- 必ず検索してから答える。知識だけで答えない
- 箇条書きで、5項目以内にまとめる
- 情報の出どころが分かるものは、それも書く
- 意見や提案は書かない。事実と傾向だけを書く"""

「必ず検索してから答える」を明記するのがポイントです。これがないと、AIは「知っているから検索しなくていい」と判断してしまいます。

⚠️ 検索を使うとトークン消費が増えます。無料枠で回す場合は、リサーチャーの並列数を減らすことも検討してください。

② ファイル操作——関数をそのまま渡す

自分で作った道具を持たせる場合も、拍子抜けするほど簡単です。

from pathlib import Path


def write_file(path: str, content: str) -> str:
    """ファイルを保存する。

    Args:
        path: 保存先のパス（例: output/index.html）
        content: 書き込む内容
    """
    Path(path).parent.mkdir(parents=True, exist_ok=True)
    Path(path).write_text(content, encoding="utf-8")
    return f"{path} に保存しました"


res = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=f"以下の仕様を実装し、output/index.html に保存してください：\n\n{design}",
    config=types.GenerateContentConfig(
        system_instruction=CODER,
        tools=[write_file],
    ),
)

Pythonの関数を、そのまま tools= に渡すだけです。

ここで重要なのがdocstring（関数の説明文）です。AIはこれを読んで「この道具は何ができて、どんな引数が必要か」を理解します。

つまり——docstringは、人間へのメモではなく、AIへの説明書になります。 適当に書くと、AIが道具を正しく使えません。

この方式の副産物として、前回書いた extract_code() が不要になります。AIが直接ファイルに書き込むので、コードフェンスを取り除く処理が要らなくなるからです。

③ ブラウザ確認——ここが本当に面倒

3つ目だけ、事情が違います。

検証役に「ブラウザで開いて、実際に崩れていないか見て」とやらせたい。ところがこれには、次のものが必要になります。

  • ブラウザを自動操作する仕組み（Playwrightなど）
  • ページを開いて、スクリーンショットを撮る処理
  • 撮った画像をAIに渡す処理（テキストではなく画像なので、渡し方が変わる）
  • スマホ幅・PC幅など、複数の条件で撮り直す処理

1つずつは難しくありません。ただ、合計するとそれなりの量のコードになります。

そしてここが分岐点です。この部分を自分で書くか、すでに用意されているものを使うか。

実は、Antigravityにはブラウザを操作するエージェントが標準で組み込まれています。実際にChromeでページを開いて確認し、その様子が記録として残ります。自分で書かずに済む道があるわけです。

これは次回、実際に組み込んで試します。

裏で何が起きているのか

「関数を渡すだけ」と書きましたが、内部では何が起きているのでしょうか。

実際のやり取りは、こうなっています。

① プログラム → AI
   「これが仕事です。あと、使える道具はこれです」
   （道具の名前・説明・必要な引数の一覧を渡す）
        ↓
② AI → プログラム
   「write_file という道具を、この引数で呼んでください」
   （AIは道具を実行できない。依頼するだけ）
        ↓
③ プログラムが、実際に関数を実行する
        ↓
④ プログラム → AI
   「実行しました。結果はこうです」
        ↓
⑤ AIが続きを考える（必要ならまた②に戻る）

重要なのは②です。AIは道具を実行できません。 「これを呼んで」と依頼するだけで、実際に動かすのはプログラムの側です。

これは安全設計でもあります。AIが勝手にファイルを消したりできない構造になっているわけです。何を実行させるかの最終的な決定権は、常に人間が書いたコードにあります。

そして先ほどのコードでは、この②〜⑤のやり取りをSDKが自動でやってくれています。 関数を渡すだけで済んだのは、そのためです。

📌 SDKによっては、このやり取りを自分で書く必要があります。その場合はもう少し長いコードになりますが、考え方は同じです。

では、限界はどこにあるのか

ここまでで、道具を持たせること自体は難しくないと分かりました。

では、素のPythonで書き続けると何が起きるのか。問題は道具そのものではなく、増えたときに現れます。

今回のチームを、道具つきで完成させると想像してください。

リサーチャー → 検索ツール
デザイナー   → （道具なし）
コーダー     → ファイル書き込み、ファイル読み込み
検証役       → ブラウザ操作、スクリーンショット、画像解析

ここで、次のような要求が出てきます。

  1. 誰にどの道具を持たせるかを管理したい。検証役にファイル書き込みを持たせたくない
  2. 道具の実行が失敗したとき、リトライしたい
  3. AIが道具を無限に呼び続けるのを止めたい（実際に起きます）
  4. どの道具がいつ呼ばれたか記録したい
  5. 途中で落ちても続きから再開したい

1つずつは書けます。でも全部書くと、本来の仕事より管理コードのほうが長くなります。

これが、素のPythonの限界です。道具が使えないのではなく、道具が増えたときの管理が重くなる——ここが正確な表現です。

そしてフレームワークが引き受けてくれるのは、まさにこの部分です。

フレームワークを入れるべき条件

判断基準を表にまとめます。

状況判断
順番に処理を流すだけ不要。関数を呼ぶだけで足りる
モデルを差し替えたい不要。むしろ素のほうが楽
独立作業を並列化したい不要。標準の ThreadPoolExecutor で十分
道具を1〜2個持たせたい不要。ここまで見たとおり簡単
役ごとに違う道具を割り当てたい検討する価値あり
失敗時のリトライ・記録が必要入れたほうが早い
途中で落ちても再開したい必要
統括が「誰に振るか」を動的に決める必要

境界線はここです。

作りたいものが増えるうちは不要。
管理したいことが増えたら、導入を考える。

💡 逆に言えば、ここまでの3回で作ってきたものは、フレームワークなしで十分だったということです。最初からCrewAIやLangGraphを入れていたら、何が起きているのか分からないまま動かしていたはずです。

まとめ

  • Web検索は組み込みツールで解決する。tools= に1行足すだけ
  • 自作の道具は、Pythonの関数をそのまま渡せる。docstringがAIへの説明書になる
  • AIは道具を実行しない。「呼んで」と依頼するだけで、実行するのはプログラム
  • ブラウザ操作だけは自前だと重い。既製の仕組みを使う道がある
  • 限界は道具の数ではなく、権限・リトライ・記録・再開といった管理にある
