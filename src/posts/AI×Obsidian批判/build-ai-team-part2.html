前回、デザイナーとコーダーの2人チームを動かしました。agent() という15行の関数だけで、役割分担が成立することを確認しました。

今回は、そこに3人を追加します。リサーチャー・検証役・統括です。

結論を先に書くと、いちばん効くのは検証役です。ここを入れるかどうかで、出来上がるものの質が明確に変わります。

今回作るもの

              統括（Pythonの関数）
                    │
   ┌────────┬───────┴───────┬────────┐
   ↓        ↓               ↓        ↓
リサーチャー×3  デザイナー    コーダー   検証役
（並列で調査）      ↓            ↓        ↓
   └────────→  仕様 ────→ 実装 ──→ 検証
                                    │
                          FAIL なら差し戻し ↑

前回との違いは3つです。

  1. 調査が入ることで、仕様の中身が具体的になる
  2. 検証役が実装をチェックし、問題があれば自動で書き直させる
  3. 調査は3つ同時に走らせるので、時間が短縮される

セットアップ（差分を追加する）

前回のプロジェクトをそのまま使います。CLIを使う場合は、次を貼り付けてください。

既存の ai-team プロジェクトを拡張してください。

## roles.py に追加
RESEARCHER と REVIEWER という文字列定数を追加する
- RESEARCHER: リサーチャー。渡されたテーマと観点について、
  要点を5項目以内の箇条書きで整理する。意見や提案は書かない
- REVIEWER: QAエンジニア。仕様と実装を照合し、
  問題なければ1行目に PASS、問題があれば1行目に FAIL と書き、
  2行目以降に指摘を列挙する。コードは書かない

## main.py を書き換え
- SMART と FAST という2つのモデル名の定数を用意する
- research() 関数を追加する
  - 3つの観点をリストで持ち、ThreadPoolExecutor で並列に
    RESEARCHER を呼び出す
  - 結果を結合して返す
- main() の流れを次のようにする
  1. research() で調査
  2. 調査結果を含めて DESIGNER に仕様を作らせる
  3. CODER に実装させる
  4. REVIEWER に検証させる
  5. FAIL なら指摘を添えて CODER に再実装させる（最大3回）
  6. output/index.html に保存
- 各工程の進行状況を print で表示する

## 注意
- agents.py の agent() は model 引数を受け取れるようにする
- 判断する役には SMART、作業する役には FAST を割り当てる

手動で作る場合は、この記事のコード全文をコピーしてください。

3つの役を追加する

リサーチャー

まず、調べる役です。

RESEARCHER = """あなたはリサーチャーです。
渡されたテーマと観点について、要点を整理してください。

- 箇条書きで、5項目以内にまとめる
- 一般論ではなく、このテーマに固有の内容を書く
- 確信が持てないことは「推測」と明記する
- 意見や提案は書かない。事実と傾向だけを書く"""

ポイントは最後の行です。「意見や提案は書かない」と明記しています。

これを書かないと、リサーチャーが勝手にデザインの提案まで始めます。そうなると次のデザイナーの仕事と重複して、両方が中途半端になります。 役割を分ける以上、境界線もはっきり書く必要があります。

⚠️ 正直に書いておくべき制限があります。 現段階のリサーチャーは、実際にWebを検索していません。 AIがもともと知っていることを整理しているだけです。

本当に調べさせるには「ツールを使わせる」仕組みが必要で、これは次回のテーマです。ただ、今の段階でも仕様の具体性は明確に上がるので、まずはこのまま進めます。

検証役——ここが品質を決める

今回の主役です。

REVIEWER = """あなたはQAエンジニアです。
仕様と実装を照らし合わせて検証してください。

【判定ルール】
- 問題がなければ、1行目に「PASS」とだけ書く
- 問題があれば、1行目に「FAIL」と書き、
  2行目以降に指摘を列挙する

【チェック項目】
- 仕様にあるセクションが、すべて実装されているか
- 指定された配色が、実際に使われているか
- スマホ幅（375px）で崩れる箇所がないか
- HTMLとして構文的に正しいか

指摘は「どこが」「なぜ問題か」をセットで書いてください。
コードは書かないでください。指摘だけを返してください。"""

設計上の工夫が2つあります。

① 1行目を PASS / FAIL に固定する

これは、あとでプログラムが判定を読み取るためです。「だいたい良さそうですが、いくつか気になる点が…」という自然な文章だと、プログラム側が合否を判断できません。

AIに仕事をさせるときは、人間が読みやすい形より、プログラムが処理しやすい形を優先する場面があります。ここがその一例です。

② コードを書かせない

検証役に修正までさせると、指摘の質が下がります。「直せるから、まあいいか」と甘くなるんです。見つける仕事と直す仕事は、分けたほうが厳しくなります。

これは人間のコードレビューでも同じで、実装者本人がレビューすると見落としが増えるのと同じ構造です。

統括——差し戻しループ

統括役は、AIではありません。Pythonの関数です。

passed = False

for attempt in range(1, MAX_RETRIES + 1):
    print(f"④ 検証役がチェック中...（{attempt}回目）")
    review = agent(REVIEWER, f"【仕様】\n{design}\n\n【実装】\n{html}", model=FAST)

    if review.strip().startswith("PASS"):
        print("   → 合格")
        passed = True
        break

    print("   → 差し戻し")
    html = extract_code(agent(
        CODER,
        f"【仕様】\n{design}\n\n【現在の実装】\n{html}\n\n"
        f"【指摘事項】\n{review}\n\n"
        "指摘を修正した、完全なHTMLを出力してください。",
        model=SMART,
    ))

if not passed:
    print(f"   → {MAX_RETRIES}回試しましたが合格しませんでした")

ここで注目してほしいのが、この行です。

if review.strip().startswith("PASS"):

この条件分岐は、100%そのとおりに動きます。 AIの気分で「まあ軽微だから進めていいか」と判断されることは、絶対にありません。

前のシリーズで、自然言語の指示だけで組んだ場合は「だいたい動くが保証はない」と書きました。その差が、この1行です。

もう1つ大事なのが、差し戻すときの指示文です。

f"【仕様】\n{design}\n\n【現在の実装】\n{html}\n\n【指摘事項】\n{review}"

仕様・現在の実装・指摘の3点セットを、毎回すべて渡しています。

コーダーは前回の会話を覚えていません。「さっきの指摘を直して」では通じないので、必要な材料を全部同封する必要があります。前回説明した「机が分かれている」ことの、実践的な帰結です。

モデルの使い分けでコストを下げる

5人全員に高性能なモデルを使うと、費用が跳ね上がります。役割によって、必要な賢さが違います。

SMART = "gemini-2.5-pro"    # 判断する役
FAST  = "gemini-2.5-flash"  # 作業する役

割り当ての考え方はこうです。

役割モデル理由
リサーチャーFAST量をこなす作業。判断は求められない
デザイナーSMARTここの判断が、最終的な質を決める
コーダーSMART仕様の解釈を誤ると全部やり直しになる
検証役FAST照合作業。基準は仕様書に書いてある

原則は「判断するところに賢いモデル、作業するところに速いモデル」です。

特にリサーチャーは3回呼ばれるので、ここをFASTにするだけで効きます。逆にデザイナーは1回しか呼ばれないので、賢いモデルを使ってもコストへの影響は小さい。呼ばれる回数を考えて配分するのがコツです。

💡 費用が気になる場合は、まず全部FASTで試してください。それで十分なことも多く、不満が出た箇所だけSMARTに上げるのが無駄がありません。

並列化できる工程、できない工程

「役割分担すると速くなる」——これは条件付きで正しい話です。

今回の流れを見てください。

調査 → 仕様 → 実装 → 検証

これは鎖です。調査結果がないと仕様は書けないし、実装がないと検証できません。どんな仕組みを使っても、順番にしか進みません。

一方、調査そのものは違います。

「構成の傾向」を調べる  ┐
「配色の方向性」を調べる ├─ 互いに独立している
「来訪者の関心」を調べる ┘

この3つは、お互いの結果を必要としません。だから同時に走らせられます。

from concurrent.futures import ThreadPoolExecutor


def research(theme: str) -> str:
    topics = [
        "同ジャンルのWebサイトによくある構成",
        "この雰囲気に合う配色の方向性",
        "想定される来訪者が知りたい情報",
    ]
    with ThreadPoolExecutor(max_workers=3) as ex:
        results = list(ex.map(
            lambda t: agent(RESEARCHER, f"テーマ：{theme}\n\n観点：{t}", model=FAST),
            topics,
        ))
    return "\n\n---\n\n".join(results)

ThreadPoolExecutor は、Pythonに標準で入っている並列処理の仕組みです。追加のインストールは不要です。

3つ順番に呼ぶと待ち時間も3倍かかりますが、同時に投げればいちばん遅い1つ分の時間で済みます。

判断基準はシンプルです。

並列化できるできない
複数の観点を同時に調べる調査 → 仕様 → 実装 → 検証
複数ページを同時に作る前の出力が次の入力になる工程
複数案を同時に出す承認を挟む手順

「互いの結果を必要としない作業か」——これだけで判断できます。

完成したコード全文

roles.py には、前回のDESIGNER・CODERに加えて、上のRESEARCHERとREVIEWERを追加してください。

main.py は全面的に書き換えます。

import re
from concurrent.futures import ThreadPoolExecutor
from pathlib import Path

from agents import agent
from roles import RESEARCHER, DESIGNER, CODER, REVIEWER

THEME = "海の見える個人経営のカフェ。落ち着いた大人向けの雰囲気"
MAX_RETRIES = 3

SMART = "gemini-2.5-pro"
FAST = "gemini-2.5-flash"


def extract_code(text: str) -> str:
    """AIの返答からコードフェンスの中身だけを取り出す"""
    m = re.search(r"```(?:html)?\s*\n(.*?)```", text, re.DOTALL)
    return m.group(1).strip() if m else text.strip()


def research(theme: str) -> str:
    """3つの観点を並列で調査する"""
    topics = [
        "同ジャンルのWebサイトによくある構成",
        "この雰囲気に合う配色の方向性",
        "想定される来訪者が知りたい情報",
    ]
    with ThreadPoolExecutor(max_workers=3) as ex:
        results = list(ex.map(
            lambda t: agent(RESEARCHER, f"テーマ：{theme}\n\n観点：{t}", model=FAST),
            topics,
        ))
    return "\n\n---\n\n".join(results)


def main():
    Path("output").mkdir(exist_ok=True)

    print("① リサーチャー3名が並列で調査中...")
    findings = research(THEME)
    Path("output/research.md").write_text(findings, encoding="utf-8")

    print("② デザイナーが仕様を作成中...")
    design = agent(
        DESIGNER,
        f"テーマ：{THEME}\n\n以下の調査結果を踏まえて仕様を作ってください：\n\n{findings}",
        model=SMART,
    )
    Path("output/design.md").write_text(design, encoding="utf-8")

    print("③ コーダーが実装中...")
    html = extract_code(agent(
        CODER, f"以下の仕様を実装してください：\n\n{design}", model=SMART
    ))

    passed = False
    for attempt in range(1, MAX_RETRIES + 1):
        print(f"④ 検証役がチェック中...（{attempt}回目）")
        review = agent(
            REVIEWER, f"【仕様】\n{design}\n\n【実装】\n{html}", model=FAST
        )

        if review.strip().startswith("PASS"):
            print("   → 合格")
            passed = True
            break

        print("   → 差し戻し")
        Path(f"output/review_{attempt}.md").write_text(review, encoding="utf-8")
        html = extract_code(agent(
            CODER,
            f"【仕様】\n{design}\n\n【現在の実装】\n{html}\n\n"
            f"【指摘事項】\n{review}\n\n"
            "指摘を修正した、完全なHTMLを出力してください。",
            model=SMART,
        ))

    if not passed:
        print(f"   → {MAX_RETRIES}回試しましたが合格しませんでした。現状のまま保存します")

    Path("output/index.html").write_text(html, encoding="utf-8")
    print("完了: output/index.html")


if __name__ == "__main__":
    main()

特に review_1.md を読んでみてください。 検証役が何を見つけたのかが分かります。ここが、今回いちばん面白い部分です。

💡 1回目で合格してしまう場合は、検証役のチェック項目を厳しくしてみてください。逆に3回とも落ちる場合は、仕様が曖昧すぎる可能性があります。

つまずいたときは

症状原因と対処
毎回3回とも FAIL になる検証役の基準が厳しすぎるか、仕様が曖昧です。design.md を読んで、具体性が足りているか確認してください
PASSと書いてあるのに合格しない1行目に説明文が混ざっています。役割定義の「1行目に PASS とだけ書く」を強調してください
429 RESOURCE_EXHAUSTED並列で3回同時に呼ぶため、上限に当たりやすくなります。max_workers=1 にすると回避できます
実行が遅いSMARTモデルは応答が遅めです。まず全部FASTで試してください
差し戻し後に内容が減る「完全なHTMLを出力してください」の指示が効いていません。より強く書いてください

まとめ

  • 役割を増やすときは、境界線も一緒に書く（「意見は書かない」など）
  • 品質を決めるのは検証役。見つける役と直す役は分ける
  • 判定は PASS / FAIL のような、プログラムが読める形にする
  • 差し戻しループをPythonで書けば、100%そのとおりに動く
  • 判断する役に賢いモデル、作業する役に速いモデル
  • 並列化できるのは、互いの結果を必要としない作業だけ

これで5人チームが動くようになりました。ただし、まだ大きな制限が残っています。

リサーチャーは、実際には何も調べていません。 コーダーはファイルを直接書けませんし、検証役もブラウザで実際の表示を見ているわけではありません。
